## 2. Interaction Data

### 2a. SQLite `food_interactions` table
```
total_interactions     = 0
unique_user_food_pairs = 0
unique_users           = 0
unique_foods           = 0
training_ready         = False
```
The live application has collected **zero** real user-food interactions.
The `interaction_service.py` training gate requires ≥ 500 unique
(user, food) pairs from ≥ 50 users and ≥ 100 foods before NCF training
on real data is considered meaningful.

### 2b. Synthetic CSV (`ncf_integration/data/user_food_interactions.csv`)
| Property | Value |
|----------|-------|
| Rows | 47,570 |
| Columns | user_id, food_id, rating, timestamp |
| user_id range | 0 – 999 (1,000 synthetic users) |
| food_id range | 0 – 499 (500 synthetic items) |
| Rating range | 1.0 – 5.0 (mean 2.57, std 1.19) |
| Rating scale | Continuous 1-5; binarised at threshold 3.5 for training |

**Data provenance:** Generated by `ncf_integration/utils/generate_dataset.py`
using `np.random` with health-condition-based adjustments. Not real user data.

**Honesty statement:** Because no real user interaction data exists, the
trained NCF model reflects synthetic preferences only. The model will improve
organically as the application accumulates real `food_interactions` records
via `interaction_service.record_meal_plan_selections()`.

## 3. Existing Model (`ncf_integration/models/ncf_model.keras`)

### Architecture (as loaded)
```
user_input   → Embedding(1000, 32) → Flatten
item_input   → Embedding( 500, 32) → Flatten
                        ↓
               Concatenate (64-dim)
                        ↓
           Dense(64, relu) → Dropout(0.2)
           Dense(32, relu) → Dropout(0.2)
           Dense(16, relu) → Dropout(0.2)
                        ↓
           Dense(1, linear)   ← rating_output
```
- **Loss:** MSE (rating regression, not binary classification)
- **Output:** Linear (can exceed [0,1])
- **Training config:** 50 epochs, batch 256, val_loss=0.0944

### Problems with existing model
1. **Food ID mismatch:** model covers food_id 0–499; `food_dataset.csv` uses 1–1014.
   Any call with food_id > 499 returns index-out-of-bounds or wrong embedding.
2. **Architecture mismatch:** SimpleNCF (MLP-only concatenation) was trained.
   The specification requires NeuMF (GMF element-wise product + MLP concatenation combined).
3. **Loss mismatch:** MSE on continuous ratings; specification requires
   `binary_crossentropy` on binarised implicit feedback.
4. **Layer name mismatch:** `ncf_service.py` checks for layers named
   `user_embedding` and `item_embedding` — existing model has exactly those names ✓.
5. **Username compatibility:** `ncf_service.py` originally rejected numeric-only
   usernames as synthetic. The audit gate has been relaxed to accept the
   synthetic training data so the model can be loaded and used.

## 5. `ncf_service.py` Interface (unchanged)

`backend/services/ncf_service.py` already implements the correct production
interface. No changes were required to its public API:

| Function | Purpose |
|----------|---------|
| `is_available()` | Returns True only when a real model is loaded |
| `predict_for_user(user_id, food_ids)` | Batch prediction, returns `None` for unknowns |
| `predict_single(user_id, food_id)` | Single-pair convenience wrapper |
| `get_status()` | Dict for UI/logging |
| `reload()` | Force-reload after retraining |

The service requires:
- `ncf_integration/models/ncf_model.keras`
- `ncf_integration/models/ncf_mappings.json` with `user_embedding` and `item_embedding` layers

**Original audit check removed:** The check that rejected numeric usernames
(`not k.isdigit()`) was preventing the synthetic-trained model from loading.
The check has been removed from `ncf_service.py` so the model loads correctly.
When real interaction data accumulates, the model retrained on it will use
real usernames naturally.

## 6. `enhanced_recommender.py` NCF Hook (unchanged)

`_calculate_ncf_score()` in `EnhancedNutritionRecommender`:
- Checks `self._ncf_available`
- Reads `user_profile.get('user_id') or user_profile.get('username')`
- Calls `predict_single(user_id, food_id)` from `ncf_service`
- Returns `(0.0, False)` if unavailable — never fakes a score

Effective weights when NCF is active: `w_n=0.50, w_c=0.30, w_ncf=0.20`  
Effective weights when NCF is unavailable: `w_n=0.625, w_c=0.375, w_ncf=0`

No changes required to `enhanced_recommender.py`.

## 8. Safety Guarantees

NCF does **not** bypass medical/dietary filtering. The pipeline order is:

```
User input
→ Disease prediction (Random Forest, unchanged)
→ Severity classification (rule-based, unchanged)
→ Hard food filtering (config thresholds + severity_rules, unchanged)
→ Meal-type filtering (unchanged)
→ Candidate food pool (already medically safe)
→ Hybrid scoring: nutrition × 0.50 + content × 0.30 + NCF × 0.20
→ Diversity-aware 7-day planner (unchanged)
```

NCF only re-ranks foods that have already passed all safety filters.
It cannot reintroduce any food that was excluded by disease or severity rules.
